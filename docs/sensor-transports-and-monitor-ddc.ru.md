# Чтение сенсора по USB и управление яркостью монитора

- [English](sensor-transports-and-monitor-ddc.md)
- [Русский](sensor-transports-and-monitor-ddc.ru.md)

Этот документ объясняет две практические части системы в её текущем состоянии:

1. как считывать и интерпретировать показания сенсора по `USB`;
2. как передавать рассчитанную яркость в монитор через `DDC/CI` и как заранее понять, поддерживает ли монитор такое управление.

## Коротко о текущем состоянии репозитория

Сейчас в этом репозитории реально реализовано:

- получение телеметрии от устройства по `USB Serial`;
- чтение newline-delimited `JSON` сообщений вида `{"id":"lumabloom","ts":1234567,"raw":1840}`;
- интерпретация поля `raw` как единственного рабочего значения сенсора;
- управление яркостью мониторов в `Windows` через:
  - `WMI` для встроенных дисплеев;
  - `DDC/CI` для внешних мониторов.

Сейчас не реализовано:

- прямое управление монитором из прошивки `ESP32-C6` по физической шине `I2C`.

Важно: в контексте ПК-приложения `DDC/CI` обычно проходит по служебным линиям интерфейса монитора и вызывается через API Windows. Это не то же самое, что напрямую управлять monitor `I2C` из `ESP32`.

## 1. Как читать и интерпретировать значения сенсора

## 1.1. Источник истины

Для текущего `ESP32-C6` источником истины является поле `raw` в телеметрии:

```json
{"id":"lumabloom","ts":1234567,"raw":1840}
```

Где:

- `id` должен быть равен `lumabloom`;
- `ts` - время с момента старта устройства в миллисекундах;
- `raw` - сырое значение `ADC`.

Поле `raw` сейчас является единственным обязательным измерением, из которого приложение считает яркость.

## 1.2. Как устроен transport в текущем проекте

### `USB`

В текущем проекте `USB` - это основной transport между устройством и `pc-app`.

Практически это означает:

- устройство появляется в Windows как `COM`-порт;
- `pc-app` сканирует доступные `COM`-порты;
- первым подходящим считается порт, который выдаёт валидные JSONL-сообщения с `id="lumabloom"` и полем `raw`.

Параметры текущего wire contract:

- скорость: `115200 baud`;
- разделитель сообщений: `\n`;
- формат: одна JSON-структура на строку;
- типичный интервал публикации: около `500 ms`.

Текущий `USB Serial` wire contract устроен как последовательный строковый поток:

- есть байтовый последовательный канал;
- есть строковый фрейминг по `\n`;
- каждая завершённая строка должна быть самостоятельным JSON-сообщением.

## 1.3. Как валидировать входящее сообщение

Сообщение можно считать пригодным к обработке, если одновременно выполняются условия:

- строка успешно дочитана до `\n`;
- строка является валидным `JSON`;
- корневой элемент - объект;
- есть строковое поле `id`;
- `id == "lumabloom"`;
- есть числовое поле `ts`;
- есть числовое поле `raw`.

Если хотя бы одно из этих условий не выполнено, сообщение не должно участвовать в расчёте яркости.

## 1.4. Как интерпретировать `raw`

В текущей реализации для обработки `raw` используются такие рабочие значения:

- `adcMin = 200`
- `adcMax = 3200`
- `invert = true`

В пользовательской конфигурации эти же параметры задаются как:

- `processing.adcMin`
- `processing.adcMax`
- `processing.invert`

Текущие встроенные значения по умолчанию в `pc-app`:

- `processing.adcMin = 200`
- `processing.adcMax = 3200`
- `processing.invert = true`

Это означает:

- `200` - это нижняя граница рабочего диапазона и в текущей схеме соответствует самой светлой сцене;
- `3200` - это верхняя граница рабочего диапазона и в текущей схеме соответствует самой тёмной сцене;
- если `raw` уходит ниже `200`, приложение всё равно считает его равным `200`;
- если `raw` уходит выше `3200`, приложение всё равно считает его равным `3200`;
- после нормализации значение инвертируется, потому что на текущей схеме больше света даёт меньшее `raw`.

### Как влияют параметры

#### `processing.adcMin`

Это нижняя граница рабочего диапазона.

Если `raw < adcMin`, приложение считает значение равным `adcMin`.

Практический смысл:

- меньшее `adcMin` расширяет рабочий диапазон вниз;
- большее `adcMin` раньше начинает считать сцену "достаточно яркой";
- слишком большое `adcMin` может сжать полезную часть диапазона и сделать систему менее чувствительной к яркому свету.

#### `processing.adcMax`

Это верхняя граница рабочего диапазона.

Если `raw > adcMax`, приложение считает значение равным `adcMax`.

Практический смысл:

- большее `adcMax` расширяет рабочий диапазон вверх;
- меньшее `adcMax` раньше начинает считать сцену "достаточно тёмной";
- слишком маленькое `adcMax` может привести к тому, что разные тёмные сцены будут выглядеть для алгоритма почти одинаково.

#### `processing.invert`

Этот флаг определяет, в какую сторону читать рост `raw`.

Если:

```text
invert = false
```

то большее `raw` означает больше света после нормализации.

Если:

```text
invert = true
```

то после нормализации выполняется:

```text
normalized = 1.0 - normalized
```

и большее внешнее освещение соответствует меньшему `raw`.

Для текущего `KY-018` на этой схеме используется именно:

```text
invert = true
```

### Формула преобразования

Сначала входное значение ограничивается рабочим диапазоном:

```text
clamped = clamp(raw, adcMin, adcMax)
```

Затем нормализуется:

```text
normalized = (clamped - adcMin) / (adcMax - adcMin)
```

Если `invert = true`, выполняется ещё один шаг:

```text
normalized = 1.0 - normalized
```

Интуитивно для текущего железа:

- `raw` около `200` означает более яркое внешнее освещение;
- `raw` около `3200` означает более тёмную сцену.

### Что важно при настройке диапазона

Если диапазон выбран удачно:

- реальные изменения света занимают заметную часть интервала `0.0..1.0`;
- алгоритм не "упирается" слишком часто в `0` или `1`;
- кривая яркости работает предсказуемо.

Если диапазон выбран плохо:

- слишком много значений будет постоянно прижато к нижней или верхней границе;
- нормализованное значение потеряет чувствительность;
- автоподстройка яркости станет либо вялой, либо слишком резкой в узком диапазоне.

## 1.5. Что делать с нормализованным значением дальше

После нормализации текущая `pc-app` прогоняет значение через brightness pipeline.

Используемые параметры:

- `adcMin`, `adcMax`, `invert` - параметры нормализации входного `raw`;
- `emaAlpha` - коэффициент экспоненциального сглаживания;
- `gamma` - необязательная gamma-коррекция после сглаживания;
- `minPercent`, `maxPercent` - допустимый диапазон итоговой яркости;
- `brightness.curve` - кривая преобразования `lightPercent -> brightnessPercent`;
- `hysteresisPercent` - минимальное изменение яркости, при котором нужно что-то применять;
- `maxBrightnessStepPercent` - максимальный шаг яркости за один цикл.

Порядок вычислений:

1. из `raw` получается `normalized` в диапазоне `0.0..1.0`;
2. `normalized` сглаживается через `EMA`;
3. к сглаженному значению при необходимости применяется `gamma`;
4. результат переводится в `requestedBrightness`;
5. `requestedBrightness` зажимается в диапазон `minPercent..maxPercent`;
6. если изменение слишком маленькое, срабатывает `hysteresis` и новая яркость не применяется;
7. если изменение слишком большое, шаг ограничивается через `maxBrightnessStepPercent`.

### Формула `EMA`

Если это не первое значение, то:

```text
ema = (emaAlpha * normalized) + ((1.0 - emaAlpha) * previousEma)
```

Если это первое значение, то:

```text
ema = normalized
```

Зависимость от прошлых значений появляется именно здесь:

- в первом цикле `ema` просто становится равным текущему `normalized`;
- в каждом следующем цикле текущее `normalized` смешивается с предыдущим `ema`;
- то есть `previousEma` - это сглаженное значение, полученное на прошлом шаге, а не прошлый `raw`.

Если расписать два соседних цикла, получается так:

```text
cycle 1:
ema1 = normalized1

cycle 2:
ema2 = (emaAlpha * normalized2) + ((1.0 - emaAlpha) * ema1)

cycle 3:
ema3 = (emaAlpha * normalized3) + ((1.0 - emaAlpha) * ema2)
```

Поэтому текущее `ema` всегда содержит в себе след от предыдущих измерений, просто чем старее измерение, тем меньше его вклад.

Чем больше `emaAlpha`, тем быстрее система реагирует на изменения света.
Чем меньше `emaAlpha`, тем плавнее, но медленнее реакция.

### Формула gamma-коррекции

Если `gamma` задана:

```text
effectiveValue = pow(ema, gamma)
```

Если `gamma` не задана:

```text
effectiveValue = ema
```

На практике:

- `gamma > 1` сильнее меняет чувствительность в разных участках диапазона;
- `gamma = 1` фактически даёт линейное поведение;
- без `gamma` используется сглаженное значение как есть.

### Преобразование в процент яркости

Если кривая `brightness.curve` не задана или в ней меньше двух точек, используется линейная интерполяция:

```text
requestedBrightness =
    minPercent + effectiveValue * (maxPercent - minPercent)
```

Затем результат округляется до целого процента.

Если `brightness.curve` задана, то:

1. `effectiveValue` переводится в `lightPercent`:

```text
lightPercent = clamp(effectiveValue * 100.0, 0.0, 100.0)
```

2. затем ищутся две соседние точки кривой:

```text
(left.lightPercent, left.brightnessPercent)
(right.lightPercent, right.brightnessPercent)
```

3. и между ними делается линейная интерполяция:

```text
ratio = (lightPercent - left.lightPercent) / (right.lightPercent - left.lightPercent)
requestedBrightness =
    left.brightnessPercent +
    ratio * (right.brightnessPercent - left.brightnessPercent)
```

Если `lightPercent` левее первой точки, берётся яркость первой точки.
Если правее последней, берётся яркость последней точки.

После этого итог всё равно ограничивается:

```text
requestedBrightness = clamp(requestedBrightness, minPercent, maxPercent)
```

### Формула hysteresis

Если уже есть ранее применённая яркость `lastAppliedBrightness`, то приложение сравнивает её с новым запросом:

```text
abs(requestedBrightness - lastAppliedBrightness) < hysteresisPercent
```

Здесь важно:

- сравнение идёт не сразу после чтения `raw`;
- сравнение идёт не с предыдущим `raw`;
- сравнение идёт не с предыдущим `normalized` или `EMA`;
- сравнение выполняется после нормализации, сглаживания, gamma-коррекции, интерполяции по кривой и ограничения диапазона;
- то есть сравниваются именно:
  - новый `requestedBrightness`, посчитанный в текущем цикле;
  - предыдущий `lastAppliedBrightness`, который был реально применён к монитору раньше.

Если условие выполняется, новая яркость не отправляется в монитор.
То есть мелкие колебания сенсора не вызывают лишних переключений.

### Ограничение максимального шага

Если изменение всё-таки нужно применить, приложение дополнительно ограничивает скорость изменения:

```text
delta = requestedBrightness - lastAppliedBrightness
```

Если:

```text
abs(delta) > maxBrightnessStepPercent
```

то вместо полного перехода берётся только один шаг:

```text
targetBrightness =
    lastAppliedBrightness + sign(delta) * maxBrightnessStepPercent
```

Иначе:

```text
targetBrightness = requestedBrightness
```

Именно `targetBrightness` уходит дальше на применение через `WMI` или `DDC/CI`.

### Что это значит practically

- `raw` не является готовым процентом яркости;
- даже `normalized` ещё не является итоговой яркостью;
- итог зависит от сглаживания, gamma, кривой отклика, ограничений диапазона, hysteresis и ограничения шага.

Именно поэтому нельзя трактовать `raw` как готовый процент яркости. Это только вход brightness pipeline.

## 2. Как отправлять яркость в монитор через `DDC/CI`

## 2.1. Что такое `DDC/CI` в этом проекте

Для внешних мониторов текущая Windows-реализация использует `DDC/CI` через `dxva2.dll`.

На уровне кода это выглядит так:

- приложение перечисляет дисплеи через `EnumDisplayMonitors`;
- получает physical monitors через `GetPhysicalMonitorsFromHMONITOR`;
- пытается читать яркость через `GetMonitorBrightness`;
- пытается выставлять яркость через `SetMonitorBrightness`.

То есть рабочая модель такая:

1. сенсор прислал `raw`;
2. приложение посчитало target brightness в диапазоне `0..100`;
3. приложение отправило этот target в Windows monitor API;
4. Windows / драйвер / мониторный стек уже доставляют команду в монитор по поддерживаемому каналу `DDC/CI`.

## 2.2. Что это значит practically для текущего проекта

В текущем проекте путь данных такой:

- `ESP32-C6` отправляет телеметрию в `pc-app`;
- `pc-app` рассчитывает целевую яркость;
- `pc-app` меняет яркость монитора через `WMI` или `DDC/CI`.

Никакой прямой `I2C`-шины между `ESP32-C6` и монитором в текущей реализации нет.

## 2.3. Как проверить поддержку управления яркостью по `DDC/CI`

Перед тем как рассчитывать на `DDC/CI`, проверяйте монитор в такой последовательности:

1. Монитор должен быть внешним, а не встроенной матрицей ноутбука.
2. В экранном меню монитора желательно найти настройку вроде `DDC/CI = On`.
3. Монитор должен быть подключён по интерфейсу и через кабель, где `DDC/CI` реально проходит.
4. Windows API должен суметь обнаружить physical monitor.
5. Должен успешно отработать хотя бы один из вызовов:
   - `GetMonitorBrightness(...)`
   - `SetMonitorBrightness(...)`

Для этого проекта практический критерий поддержки такой:

- если монитор находится через `DdcMonitor.Discover()`, это ещё не гарантия полной поддержки;
- если `GetMonitorBrightness(...)` или `SetMonitorBrightness(...)` стабильно возвращают успех, монитор можно считать пригодным для `DDC/CI`-управления;
- если оба вызова не работают, монитор нужно считать неподдерживаемым для этого способа.

## 2.4. Как ведёт себя текущая реализация

Текущая реализация уже делает разумную проверку:

- сначала пытается обнаружить monitors через `WMI` и `DDC/CI`;
- для `DDC/CI` на запись пробует прочитать диапазон яркости;
- если диапазон прочитать не удалось, всё равно пробует `SetMonitorBrightness(...)` с процентом `0..100`;
- если запись не проходит, монитор помечается как проблемный.

Это полезно, потому что некоторые мониторы плохо отвечают на чтение, но принимают запись.

## 2.5. Как practically считать монитор поддерживаемым

Для текущего проекта монитор practically можно считать:

- `supported`:
  - обнаружился как физический монитор;
  - хотя бы одна тестовая установка яркости прошла успешно.
- `partially_supported`:
  - чтение текущей яркости не работает;
  - запись работает.
- `unsupported`:
  - монитор не обнаруживается как управляемый;
  - или запись яркости завершается ошибкой.

## 2.6. Какой порядок действий должен быть в приложении

Правильный порядок выглядит так:

1. обнаружить кандидатов на управление яркостью;
2. разделить встроенные дисплеи (`WMI`) и внешние (`DDC/CI`);
3. для каждого монитора проверить практическую возможность чтения/записи;
4. только после этого включать автоматическое применение brightness updates;
5. при повторяющихся ошибках отключать конкретный монитор, а не ломать весь sensor pipeline.

Именно такой подход лучше всего переживает частично совместимые мониторы.
